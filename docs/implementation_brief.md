# 实施说明

## 目标

把飞书中分散的数据需求、背景、角色、承诺和进度自动整理为私人 PM 工单，让系统主人即使忘记上下文，也能通过简洁 `describe` 恢复任务全貌。

## 使用者

- **系统主人**：查看候选、确认任务、安排私人计划、跟进、归档和回收站恢复。
- **需求提出人**：继续使用原来的飞书私聊或群聊，不要求学习新系统。
- **协作者**：只有在确实需要多人确认时，才进入按需建立的需求群。

## 入口

1. 需求方直接私聊系统主人：主人授权后，系统分页发现 OAuth 可见的既有 P2P 并保存对方 `open_id`，但新发现人员默认不关注；主人逐个选择或点击“关注所有人”后，程序才周期读取对方新消息。该按钮只作用于当前列表，不能声称实时或覆盖飞书 API 未返回的全部私聊。
2. 群聊中 `@系统主人`：用户 OAuth 发现主人所在群；主人按群名选择后分页读取近期历史，并只把本地 mentions 匹配到主人的消息送入候选判断。该主链不要求机器人在群内。
3. 个人日历：增量读取新增、修改和取消日程，只形成需求或排期线索。
4. 会议内容：增量读取被允许访问的妙记和转写。
5. 机器人补充入口：机器人私聊和明确授权重点群的实时消息。
6. 人工补录：转发给机器人，或明确说“把这条记成任务”。

以上消息若包含飞书 Docx，或实际指向 Docx 的 Wiki 链接，系统可在主人原有权限范围内读取受限正文片段作为需求背景。文档是来源的派生上下文，不新增第七类主入口；无权限、失效或暂不支持时必须保留原消息并明确降级。

飞书企业自建应用负责用户授权和 API 权限；不能要求需求方主要与机器人对话。

## 输出

- 候选收件箱：固定展示时间范围、背景、希望验证、Describe 和识别依据，再由主人接受、暂存或忽略；不在前端直接展示聊天正文。模型尚未成功生成摘要时不创建候选卡。
- 可靠需求整理：结构失败由 Runtime 自动恢复，最终失败只保留来源和恢复工作项；疑似漏掉前文时只在已启用会话内有界补扫；连续消息可拆为多个具体需求单元，并分别关联已有需求线或私人任务。
- 私人任务台账：工作台、全部任务、私人排期日历、归档与回收站。
- 任务记忆：来源摘要、`describe`、提出人、角色、状态、时间线、风险、产物位置；原始聊天正文只作为受控来源审计事实保存。
- AI 修改审计：明确证据下自动维护私人任务，展示前后值、来源、模型和双重置信度；主人可撤销、完整编辑、切换仅建议或暂停单项任务。
- 私下提醒：新候选、范围或承诺变化、延期风险、疑似交付、每日摘要。

## 持续对话判断

每条来源先由 LLM 判断消息动作，再由服务端决定是否能安全写入：

1. `new_demand` 才创建新的候选；`update_existing` 进入已有需求线程的稀疏更新；`context_only` 只保留上下文；主人消息另走 `owner_decision` 状态机。
2. LLM 只能从服务端提供的匿名候选快照中选择线程。服务端重新检查完整评分、候选集 hash、来源 revision、线程/任务版本、授权主人身份和自动维护策略。
3. 交错需求无法唯一判断、动作置信度不足、模型结构失败或日期语义需要确认时，来源仍落库并进入 `needs_confirmation` / Runtime 重试，不随机新建候选或修改任务。
4. 日期表达由程序按消息发生时间和上海时区换算；LLM 另外标注截止、开始、范围或仅参考。需求方询问的日期默认需要确认，主人明确确认后才可进入私人计划。
5. DeepSeek 使用分阶段小结构：普通消息先判断动作，再按需调用关联、归并和详情阶段；已验证的主人消息直接提取接受、拒绝、转交、确认时间或索要资料意图。模型只处理语义，服务端负责 ID、日期、候选选择、默认值和最终业务对象；关联不唯一时保留判断但不执行。

验收不能只发送一条孤立消息；应回放完整多轮对话，逐轮检查候选数量、需求线程归属、任务版本、时间线事件和待确认通知。当前 Issue #23 的回放覆盖连续承接、交错需求、待接受候选补充、跨天/跨 30 天、日期边界、重复投递、结构失败和低置信降级；PR #24 另用真实 `OpenAICompatibleClassifier` 走完五轮 DeepSeek 兼容回放，不能只用返回固定结果的假分类器代替。

## 需求标识

- `source_event_id`：按 `external_id` 保存的最新授权来源状态；编辑、撤回或补充可能原地更新当前行。当前尚无 append-only revision/history，因此不能把它描述为不可覆盖的原始消息。
- `demand_unit_id`：消息或连续消息中的一个具体需求；同一消息可参与多个单元。
- `requirement_thread_id`：围绕一个需求持续补充和修改的对话线。
- `task_id`：主人接受后建立的私人正式任务。

模型、归并和人工纠错都必须以需求单元为最小业务边界，不能因为共享原始消息而把另一个需求一起移动或改写。

## 不在系统职责内

- 自动完成数据分析。
- AI 可在明确来源证据和安全门禁下更新私人内部状态与计划；不能替主人对外承诺负责人、优先级、交付日期或宣布完成。
- 自动向外部人员发送承诺。
- 自动修改关联工作区中的真实文件。
