# AI 虚拟数据分析 PM：大原型场景地图

记录日期：2026-08-08

更新日期：2026-08-09。当前阶段统一结论见 [product_prototype_closure_20260809.md](product_prototype_closure_20260809.md)。

## 一、统一产品概念

这不是单一的提单机器人，而是一个存在于飞书中的“数据分析需求协作中枢”。它从需求出现前后开始持续感知信息，把不同来源的事项整理到用户私有的候选需求收件箱，再由人确认是否进入正式 PM 流程。

```text
私聊机器人
直接私聊系统主人
指定群聊新消息     ──> 候选需求收件箱 ──> 人确认 ──> PM 台账 / 排期
会议事项捕捉                                      └─> 原对话 / 按需拉群 / 跟进
机器人人工补录
```

“候选”与“正式任务”必须分开：AI 可以发现和建议，但不能因为一句模糊聊天就自动制造正式工作承诺。

### 任务识别的中间层

所有来源先经过“候选事项”层。AI 先识别事项类型和责任线索，再把内容分为：明确可能由系统主人负责、可能相关待确认、仅作背景/他人工作三类。候选事项保留判断依据和原始来源，但不进入正式排期、负载或承诺统计；系统主人确认后，才生成正式任务。

候选事项的识别、关联、去重和背景归档默认由 AI 在系统主人的私人空间自动完成，不要求逐条审核。任何内容只要准备让系统主人以外的人看到，就必须先经过系统主人确认。

## 二、主要场景

### 1. 需求方主动私聊机器人

- 触发：需求方直接向飞书机器人描述一个想法或问题。
- AI 行为：用自然语言追问背景、为什么想用数据验证、希望支持什么判断；然后复述理解。
- 人的决定：确认机器人是否理解正确，以及是否值得进入分析流程。
- 产出：一条候选需求。
- 当前定位：正式需求入口。

私聊是即时交互入口：收到消息后立即回应，不等待周期汇总。

系统主人可以事前授权标准接待和澄清流程。机器人可以自动询问背景、为什么需要数据、希望支持什么判断，并复述理解；但不能代表系统主人接单、排期、确定负责人、拉群或作出正式表态。完成信息收集后，只向需求方说明“已记录并转交确认”。

转交门槛采用“够用就转交”：背景、数据验证原因和希望支持的判断已经清楚，就生成候选需求。数据对象、口径、交付形式和具体时间可以作为待补充项，留到系统主人接收后再讨论。

任何入口一旦形成新的候选需求，都立即私下提醒系统主人；提醒不代表必须立即处理，候选仍保留在私人收件箱。普通消息、背景和既有任务进展不逐条提醒。

候选提醒只提供“接受、暂存、忽略”三个主要动作。接受只进入私人正式台账，不自动对外回复；暂存继续留在候选收件箱；忽略保留可恢复的来源与处理记录。合并、去重和关联已有任务由 AI 自动完成。

### 2. 需求方直接私聊系统主人

- 触发：需求方仍然按原习惯直接给系统主人发消息。
- AI 行为：在明确授权的会话范围内旁路理解新增对话，识别潜在需求、提出人、背景、数据验证目的和系统主人已经作出的承诺。
- 人的决定：收到候选需求提醒后，选择接受、暂存或忽略。
- 产出：带原始私聊来源的私人候选需求。
- 当前定位：核心需求入口，解决“现实中别人通常还是直接来找我”的问题。
- 对话行为：AI 默认不在原私聊中发言；需要回复、澄清或对外表达时，仍经过可见性门禁。

### 3. 指定群聊的新消息监控

- 触发：用户选择需要关注的群；群内出现新增消息后，对尚未判断的新增内容处理一次。底层可以研究事件订阅、轮询或心跳，但产品触发语义统一为“有新消息就判定一次”。
- AI 行为：发现提到用户、数据分析、承诺时间、需求变更、待办或风险的内容，提炼相关上下文。
- 人的决定：忽略、保存为待办、合并已有任务，或转成候选需求。
- 产出：候选事项或候选需求，不直接创建正式任务。
- 当前定位：高优先级场景，重点解决“我在群里但没看到所有相关信息”。

群聊是监控入口：每批新消息只做一次相关性与责任判断；相关才记录到候选收件箱，不把群聊变成连续对话窗口。

第一版相关性规则为“明确指向 + 既有任务上下文”。明确指向包括 @、点名、直接分配和系统主人已作出的承诺；既有上下文包括与已有任务的主题、范围、时间、结论或待办有关。一般闲聊或孤立关键词不触发。候选必须展示判定依据和置信程度，方便系统主人纠正。

### 4. 会议结束后的事项捕捉

- 触发：会议结束并有可用的纪要、转写或摘要。
- AI 行为：提取数据相关事项、隐性承诺、未决问题、负责人和可能的截止时间。
- 人的决定：确认哪些内容真正需要进入 PM 系统。
- 产出：用户私有的候选需求/候选待办。
- 当前定位：高优先级场景；目标是会后提醒用户，不在会议中打断参与者。
- 边界：是否允许低可见度或无感捕捉，必须后续研究平台能力、组织政策、参与者告知和信息留存边界。

会议是会后入口：内容可用后再生成候选事项，不在会议中即时打断。

### 5. 私有 PM 管理台

- 触发：用户需要查看未来工作和当前风险。
- AI 行为：把候选需求、正式任务和讨论记录整理成简单视图。
- 人的决定：确认优先级、承诺时间、暂停或取消任务。
- 产出：只对用户/团队可见的任务总览。
- 建议视图：候选需求、待确认、已承诺、执行中、等待他人、临近截止、存在风险。

### 6. 原对话优先与按需拉群

- 默认：候选需求被接受后继续在原私聊或原群聊推进，不自动新建群，也不要求机器人加入。
- 拉群触发：多人必须共同确认、上下文分散，或后续需要持续多人协作。
- AI 行为：在私人空间准备成员、理由、群名、用途和开场摘要；成员按唯一飞书身份核验。
- 人的决定：确认是否拉群、成员、范围、交付物、负责人和正式排期。
- 产出：原对话中的协作记录，或用户确认后建立的按需协作群。

### 7. 后续跟进与历史复用

- 触发：任务临近承诺时间、长时间没有进展、需求方询问状态，或出现相似新需求。
- AI 行为：每日发送低密度摘要，提醒风险、汇总最近变化、查找历史类似任务和过去耗时。
- 人的决定：改期、调整范围、继续推进或关闭任务。
- 产出：状态更新、复盘记录和可复用经验；普通变化自动写入，正式完成仍由人确认。

### 8. Agent 工作区 reference path

- 触发：正式任务需要在 Cindy、Claude、Coze、ChatDev 或其他 Agent 工作区中执行。
- AI 行为：在指定位置建立本地任务目录，用 `reference path` 关联实际工作目录，并读取授权范围内的文件清单、变化和可能的产物位置。
- 人的决定：授权读取位置、修正失效路径并确认最终交付。
- 产出：工单与实际工作文件位置的可追溯关联。
- 边界：不复制归档、不写入、不移动、不覆盖、不删除实际工作文件。

## 三、当前重点与后续想象

### 当前重点

- 需求方直接私聊系统主人的自然对话捕捉。
- 指定群聊的持续监控。
- 会议结束后的数据事项捕捉。
- 用户私有的 PM 任务总览。
- 候选需求收件箱与人工确认机制。
- 每日摘要、日历排期建议和任务风险提醒。
- 与本地 Agent 工作目录的只读 reference path 联动。

### 后续再研究

- 从模糊聊天中自动触发正式数据需求。
- 多名分析师之间的智能路由和自动分配。
- 根据历史耗时预测排期。
- 自动代表分析师与需求方进行优先级博弈。

## 四、共同设计原则

1. **简单入口**：用户自然说话，不填写复杂表单。
2. **候选与正式分离**：AI 发现不等于任务成立。
3. **低打扰**：监控和会议捕捉默认不在现场频繁插话。
4. **人工掌握承诺**：成员、范围、优先级和交付时间都要有人确认。
5. **隐私优先**：只监控明确授权的群和资料，保留范围与时间可控。
6. **可追溯**：每个候选需求都能回到来源上下文和后续决策。

## 五、后续场景卡模板

后续新增场景时，先记录五项：

- 触发者与触发时刻。
- 用户当时想完成什么。
- 当前做法为什么麻烦或容易出错。
- AI 应该做什么，哪些决定必须由人做。
- 最终沉淀为候选事项、正式任务、提醒还是历史知识。
