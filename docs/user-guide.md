# TooManyTasks 使用与验收指南

本文面向不熟悉软件工程的使用者。产品阶段、源码基线、遗留安装包和真实环境边界只查 [当前状态](current-state.md) 与其中的验证 ID；本指南只说明怎样操作，不把历史记录重新写成当前验收结论。没有对应凭证或权限时只能完成 Mock/契约验收，不能把未测试来源写成“真实连接已验证”。

## 1. 打开当前入口和数据位置

当前使用入口是 **Cindy 插件 + 本机后台 + 浏览器**：

1. 在 Cindy 安装并开启插件 **TooManyTasks 入库**（`plugins/cindy-pm-intake`）。
2. 在 Cindy 连接 **XD Feishu**。
3. 对话里说「扫近10分钟」。插件会在本机拉起任务库后台，默认地址为 `http://127.0.0.1:4310`。
4. 浏览器打开该地址，使用工作台、候选箱、任务详情和设置页。设置页可以重启后台，成功后当前页面继续可用；退出后台后页面会失去连接。

现行流程从 Cindy 插件开始；浏览器设置页只管理本机任务库运行选项，不提供旧飞书 OAuth 首配。飞书连接由 Cindy 的 XD Feishu 插件负责。

数据保存在本机 SQLite。Cindy 退出后后台一起停；再次说「扫近10分钟」可以重新拉起。没有凭证时，可使用安全模拟模式与人工补录完成本机候选和任务管理验收。

开发者需要本地改网页和接口时，在仓库根目录运行 `npm install` 和 `npm run dev`，打开 `http://localhost:5173`；生产式预览运行 `npm run build` 和 `npm start`，打开 `http://127.0.0.1:4310`。页面操作与下文相同。

旧桌面安装与 OAuth 首配步骤仅作为历史记录保留，当前使用请按上面的 Cindy 插件与浏览器入口操作。

## 2. 无凭证时可以验证什么

“安全模拟模式”表示不连接真实飞书或真实模型，不代表正式 App 会开放开发用消息写入接口。正式构建不注册 `/api/dev/simulate-message`，设置页也不提供“虚拟消息测试”。维护者仍可在显式测试装配中用人工构造数据验证收件链路，但测试结果只能记为 Mock/契约验证。

候选列表与操作结果、任务列表/详情/工作台/日历/提醒、重新整理、纠错记录和主人信息默认只显示公开白名单字段；来源信息仅包含来源类型、完整性、发生时间和摘要是否可用。聊天正文、来源稳定 ID、外部 ID、provider/model/prompt、文档 URL/ID、参考路径、纠错原始快照/备注和 Runtime 原始错误不会进入这些默认响应。若要核验一项来源，请在任务详情点击“主人核验来源”并明确确认；服务端会按 opaque 来源范围重新检查任务关联，只返回有界脱敏片段并记录私有审计，不发送消息、不打开外部工具，也不会创建对外动作。

没有凭证时，系统主人可以通过正式的人工补录入口验证本机候选和任务管理：

```text
日志与纠错 → 人工补录漏掉的需求
→ 候选收件箱 → 接受为正式任务
→ 任务详情 → 编辑任务 → 修改字段与私人计划
→ 排期日历 → 确认任务出现 → 清除安排
→ 删除任务 → 归档与回收站 → 恢复任务
→ 任务详情 → 任务记忆 → 清理并重建
→ 任务详情 → 参考路径 → 挂接并解除引用
→ 生成对外更新草稿（只进入待确认）
→ 任务详情 → 纠错 → 记录私人纠错
→ 日志与纠错 → 查看判断、重试和纠错记录
```

连续对话、模型结构失败、自动更新和真实来源同步不属于上述人工补录验收；这些能力分别使用显式测试 App 的契约回放或另行 L6 真实环境验收，不能从人工补录结果外推。

人工补录后的本地操作，以及维护者在显式测试 App 中执行的其余 Mock/契约回放，应分别看到：

- 相同 `message_id` 重复进入不会重复建单；
- 工作台标题与“今天推进”固定按上海自然日计算；显式计划区间覆盖今天的跨日任务也会显示，completed 不再算待推进，archived 默认隐藏。页面列表只展示前几项，但括号中的候选、今日计划和等待总数不受列表上限影响，“进行中”和“已逾期”也按各自状态/截止条件独立统计。底部会如实显示本地模拟模式或外部适配器已配置，后者只表示装配状态，不代表真实租户范围已经验收；
- 工作台、候选、任务、排期、归档和设置页会明确区分读取中、成功但为空、读取失败、成功有数据和刷新后数据可能已过期。读取失败不会显示成“没有数据”或“0 项”；刷新失败会保留上次成功内容并标出过期提示，页面提供“重试”。同一资源的读取和保存/处理操作只接受最新一轮结果，迟到的旧结果不会覆盖刚完成的标记已读、主人刷新、来源同步、自动维护模式或关注范围保存。工作台提醒独立读取，因此主工作台失败时仍可看到提醒并安全处理。本轮 Issue #51 的可复核证据见 `VER-ISSUE51-UI-L4-20260816`；它只证明 Mock/合成浏览器 L4，不代表真实飞书、Electron/NSIS L5 或 provider L6。
- 候选接受后才出现正式任务；
- 候选可以在卡片底部点击“移入回收站”；未接受候选只影响自身，已接受候选会和对应正式任务一起进入回收站。切换“回收站”后可恢复，已接受候选和任务也会一起恢复；来源、通知审计和关联仍保留；
- 保存计划后，全部任务和排期日历显示相同的开始/完成时间；日历固定按上海自然日归组，跨日任务出现在每个实际覆盖日，区间结束恰为 00:00 时不进入右侧日期，起止相等则作为单日点事件显示。单项计划最多覆盖 366 个上海自然日；任务编辑、主人消息确认排期、“状态或排期有误”纠错，以及撤销 AI 自动维护时恢复的计划会拒绝超限或反向区间。旧自动更新的 before/after 快照会使用同一严格 parser；数字、布尔值和看似日期但不是 ISO datetime 的字符串都会被拒绝，线程、候选或修订 ID 错配也只显示固定脱敏冲突。涉及候选修订的撤销还必须找到唯一 previous revision，并确认恢复前后内容与 candidate_request 一致，避免撤销后没有 current revision 或候选摘要分叉；候选的 pending/snoozed/ignored/accepted 业务状态不会由旧快照改写。失败时任务、提案、线程、候选、候选修订与时间线保持不变；合法历史额外字段会被忽略，不进入恢复后的任务或新审计。旧数据依次使用首个可解析的 `planned_start_at → planned_due_at → schedule_at`；部分坏字段会在 Calendar 专用响应中清成空值并使用有效 fallback，全坏、超限或反向任务会被逐项隐藏。页面只显示固定脱敏提示和隐藏数量，其他正常任务继续显示。completed 保留在原计划日，archived、已作废和回收站任务默认隐藏；清除安排后日历不再显示该任务；
- 日历事件与任务候选是两类东西：普通提醒、仅出席会议、全天/重复、节假日、生日和订阅日历默认只在 Calendar 中保留为来源事实；只有明确“主人负责什么 + 要做什么 + 交付什么/何时截止”才会出现待确认候选。责任不明时只显示待主人确认原因，不批量生成候选；会议 action item 以纪要或明确消息为依据，不能由会议占位推断。分类路由可由受限 `/api/calendar/sources` 查看，来源事实不会因分类而删除；真实飞书字段和租户范围仍需验收。
- 删除会把任务和对应的已接受候选一起移到回收站，恢复时双方一起回到活动页面；来源、时间线和参考路径始终保留；
- 来源摘要、提出人、低密度结论单和详细 describe 可回查；聊天正文不在候选卡或任务详情直接展示，仍保留在本地来源审计中；保存排期、状态或自动维护设置后，页面继续保留完整任务详情，不会因为最小化来源响应而丢失持续更新、来源或时间线区域；
- 强回复链、唯一归属、模型未降级且双重置信度达标时，后续消息可自动更新私人任务；弱关联、推测时间或版本冲突只进入待确认；
- “AI 最近修改”可查看前后值、来源、模型、置信度和原因；只要该修改仍是任务最新版本即可撤销，存在后续修改时会拒绝覆盖；
- 全局“仅建议”或单任务暂停后，消息仍会保存，但不会自动修改正式任务；
- 任务详情可完整编辑标题、Describe、下一步、风险、等待原因、状态和私人计划时间，保存后刷新任务记忆；
- “清理并重建”只删除系统托管的标准投影，目录中的未知文件继续保留；解除参考路径只删除绑定和快照，不触碰真实目录；
- 工作目录只显示目录元数据，不改变任务完成状态，也不修改真实文件；
- 对外动作只会生成本地草稿：页面显示“待主人审阅 / 已拒绝 / 已失效”，不显示“可发送”或“已确认发送”；M1 没有发送按钮、发送接口或后台发送。重复生成同一版本的同一草稿不会堆积，任务删除、改判无效或来源失效会原子终止草稿，恢复任务也不会重新打开旧草稿；
- 纠错只产生私人时间线和 `correction_event`，不会发消息、拉群或执行业务任务。
- 如果主人把已接受的记录改判为“这不是需求”，系统会保留原文、来源链和审计，把正式任务标记为“已判定非需求”并归档；它会从工作台、等待区和日历中隐藏，也不能再生成对外动作。

### 完整编辑、排期、删除与恢复

1. 打开正式任务并点击“编辑任务”，可修改标题、Describe、下一步、风险、等待原因、状态、计划开始和计划完成；完成时间不能早于开始时间。
2. 保存使用当前任务版本。若 AI 或另一个页面已经更新任务，旧页面会收到版本冲突，刷新后再决定，不能静默覆盖新内容。
3. 手动修改会标为“主人手动”；如果是在 AI 修改后纠正，则保留 AI 原事件和新的人工纠正事件，并重新生成任务记忆。
4. 点击“清除安排”可同时清空开始和完成时间；如果任务原本只是“已排期”，状态会回到“待排期”。这些时间只属于私人工作台、列表、日历和本机提醒，不会通知需求方。
5. 点击“删除任务”后，任务进入“归档与回收站 → 回收站”，并从工作台、全部任务、日历和提醒中移除。
6. 在回收站打开任务并点击“恢复任务”即可恢复。来源、时间线和 `reference path` 一直保留；此前因删除而作废的对外草稿不会自动恢复。

回收站属于可恢复的私人任务管理，不等于隐私数据永久删除。隐私生命周期入口位于设置页，流程是“停止采集/撤销本地授权 → 可选导出 → 二次确认硬删除”。硬删除只保留不含内容的删除证明和必要审计；不能用“清理运行日志”或清空回收站代替。平台侧 Feishu 撤权、第三方备份残留和法律合规不在本地合成验收范围。

### 隐私生命周期

1. 在设置页点击“停止采集”。后续受管同步会返回固定的 `PRIVACY_COLLECTION_STOPPED`，不会继续采集；这一步不会删除已有来源。
2. 如果要阻止本地重新采集，点击“撤销本地授权”。本地 token/scope、监控开关和 Feishu 游标会停止或清理；页面会明确平台侧撤权尚未验证。
3. 如需保留副本，点击“导出数据”。导出 scope 和格式受控，重复幂等键复用同一 payload/hash。
4. 点击“请求硬删除”，复制页面显示的确认凭证，再点击“确认硬删除”。服务端会核对删除请求、确认 hash 和隐私版本 CAS；冲突不会静默成功。
5. 成功后只保留无内容的删除证明、计数、hash、状态和必要审计。任何失败都会回滚业务删除，不会留下半套结果。

数据库备份只能通过受管目录创建和校验。在线“验证备份”只会返回校验结果和 `requiresRestart`；真正替换打开中的 SQLite 必须先退出服务，再从受控维护入口恢复。Windows 文件锁、真实用户历史库、平台备份残留和 L5/L6 尚未验证。

### 候选收件箱回收站

候选页和任务页保留各自的回收站入口，但已接受候选与正式任务共享同一个回收状态。候选卡片或任务详情任一侧执行删除，双方都会一起进入回收站；任一侧恢复，双方也会一起恢复。未接受候选仍只影响候选自身。所有操作都保留原始飞书来源和审计；若主体卡已经合并多条候选，移入和恢复会处理整个归并组。

在手机窄屏上，候选操作按钮按单列显示；“恢复到稍后再议”位于卡片内容下方，不会覆盖其他按钮。若看不到删除按钮，请先确认当前不是“回收站”筛选，且候选卡仍处于活动列表。

### 多条候选属于同一个需求

两条消息即使来自同一个人，也不一定是同一需求。系统会同时判断业务对象、目标、交付物和明确延续关系，并判断哪条是“你需要推进的主体任务”。

- 高置信且主体唯一时，候选收件箱只显示一张主体卡，并写明“已合并 N 条候选消息”和主体理由。
- 展开“查看来源摘要并纠正”后，每条来源仍独立可见，并标记为“你要推进的主体、需求背景、约束条件、流程咨询”或“作用待确认”；这里显示 AI 摘要和归类依据，不直接显示聊天正文。
- 若主体选错，可在接受前点击“设为主体”；若两件事被误合并，可点击“拆成独立候选”。
- 低置信时两张候选都会保留，并显示黄色归并建议。你必须选择主体后确认合并，或点击“保留为两件事”；确认前不能接受为正式任务。
- 归并组的接受、稍后再议、忽略、移入回收站和恢复都会处理整组。接受后只建立一个正式任务，并挂上组内全部原始来源。
- 正式任务建立后，候选阶段的“换主体 / 拆分”入口会变为只读；若后续发现归属错误，应在正式任务的纠错与线程迁移入口处理。

### 持续补充同一个需求

系统不会把每一条后续消息都当成新任务。它按以下顺序尝试接回原需求：

1. 飞书回复链的 `root_id` / `parent_id`；
2. 明确任务引用、稳定的同一 `session` 和主人已经确认过的归属；
3. 同一会话、同一参与人和近期时间窗，并且消息明确写出“补充、追加、继续”等表达；
4. 若同时存在多个可能线程，保留候选关联并显示“待确认”，不会只凭关键词或模型提示强行合并。

这里的“判断”由 LLM 完成，程序不靠关键词直接决定需求归属；程序负责把 LLM 的判断限制在服务端提供的匿名候选快照内，并复核完整评分、置信度、来源版本、任务版本和日期证据。只有 `new_demand` 会增加候选，待接受候选的后续补充会回到原需求单元；低置信、模型降级或无法唯一判断时，来源会保留在“待确认”提醒中，不会静默丢失或随机改任务。

连续消息的预合并首先保证同一会话在同一次完整分页扫描批次内生效。跨轮询时，“可以”“什么时候要”“策划案在哪”等自然短句还可以在 30 分钟内承接唯一近期需求；明确说“另一个/新需求”会保持拆分。实时 WebSocket 多消息缓冲尚未实现；分别形成的待确认候选仍会再次参加语义归并。原始消息始终逐条保存，不会被合并摘要替代；页面只呈现 AI 摘要和归类依据。

如果模型发现同一批消息其实包含两件独立工作，会拆成两张“具体需求”卡；一条同时提到两件事的消息可以同时出现在两张卡的来源中。页面中的标识含义是：原始消息 ID 只代表那句话，需求单元 ID 代表其中一件事，需求线 ID 串起这件事的后续对话，任务 ID 则是接受后建立的私人任务。拆分、改挂或纠错只处理当前需求，不会把共享消息对应的另一件事一起移动。

疑似只收到“再补一个海外口径”这类后半段时，系统会在该人员或已选群的启用范围内向前补扫，最多回看 72 小时和 3 页，并遵守重新启用时的硬起点。补扫不会移动日常同步水位；你自己此前说过的话只用来理解背景，不会单独生成任务。若达到页数、时间、权限或启用边界，卡片会标记“背景不完整”，需要你查看来源后确认。

后续需求方消息一定先进入原始来源链，再生成带任务版本、线程版本、证据、模型和双重置信度的“任务更新提案”。系统主人自己的消息会进入独立的“主人判断”记录：它不会生成普通候选，但可以在目标唯一且证据充分时承接候选或维护私人任务。主人消息必须匹配当前 OAuth 已授权主人的稳定 ID，意图置信度还要达到 `0.90`；伪造主人标记或低置信结果只留待确认。需求方消息的“AI 自动维护”以及主人判断的自动动作都必须通过归属、模型、置信度、版本和暂停状态安全门；任一条件不满足就留在待确认，不会偷偷覆盖正式任务。若候选在判断期间被忽略、删除或关联任务被作废，旧判断只保留为 `stale` 审计，不会因恢复候选或任务重新进入待确认；无法证明 ignored 候选的退休时间，或只有同会话而没有强来源关系的旧孤儿判断，会继续显示待确认而不擅自判 stale。

AI 可自动维护标题、Describe、下一步、风险、等待原因、内部状态、私人计划时间和需求线程内容。`completed / archived` 必须有明确的完成、取消或不再处理证据，并会重点提示；删除任务、判定“这不是需求”和物理清除数据永远不能由 AI 自动执行。设置里可把全局模式切为“仅建议”，任务详情也可暂停单个任务；两种情况下来源照常保存。

每次自动修改都会生成独立审计记录和“AI 最近修改”卡片，显示修改前后、来源、模型、置信度、原因和时间。若该次 AI 修改仍是任务最新版本，可一键撤销；如果之后已经有人工或新的 AI 修改，系统会返回版本冲突，要求主人直接编辑最新任务，避免撤销覆盖后续工作。

提醒统一出现在“工作台 → 需要关注”。自动应用成功时只显示“AI 已自动维护”；安全门未通过时才显示“请确认更新”，同一来源不会同时保留两种未读提醒。点击提醒会先标记已读，再打开对应任务；完成或归档会显示需要重点核对的提醒。

接受任务后，系统会在配置的任务记忆根目录下创建稳定目录：

```text
tasks/<task-id>-<标题>/
├─ task.json       当前任务与版本
├─ brief.md        已确认的背景、Describe 和下一步
├─ sources.md      来源索引、标识哈希和正文哈希
├─ updates/        每次确认更新的历史
└─ artifacts.json  只读工作目录的元数据索引
```

SQLite 仍是唯一真源，文件夹是可重建投影；因此待确认提案不会提前写入 `brief.md`，AI 自动修改、主人手动编辑、纠错、删除和恢复都会触发受控重建，投影失败也不会回滚正式任务。遗留 Windows EXE 会自动把任务记忆放在自己的应用数据目录；在任务详情的“持续更新 → 任务记忆目录”可以重试、清理并重建，或点击“打开任务记忆目录”。

“清理并重建”只清理系统明确托管的 `task.json`、`brief.md`、`sources.md`、`artifacts.json` 和已登记的 `updates/` 文件，不递归删除整个任务目录，也不删除未知文件或用户自有附件。参考路径与任务记忆目录是两件事：解除引用只删除 SQLite 中的绑定和对应快照，真实工作目录仍然只读，不会被删除、移动或修改。

## 3. 首次真实飞书连接（遗留桌面流程）

> 以下步骤仅保留旧版桌面端的历史记录；现行用户通过 Cindy 的 XD Feishu 插件连接飞书，浏览器设置页不再提供这些 OAuth 配置项。

真实连接需要系统主人自己在程序内填写，不要把 App Secret、用户令牌或 LLM Key 发给协作者。

1. 在飞书开放平台创建“企业自建应用”并发布一个可用版本。主人个人信息流使用用户 OAuth；机器人只在你确实需要机器人私聊、转发或补充群时再开启。
2. 配置应用回调地址：`http://127.0.0.1:4311/oauth/feishu/callback`。端口被占用时先关闭占用程序，或改成一个本机未占用端口并同步到开放平台。
3. 在开放平台按实际用途申请最小权限：主人 P2P/群消息读取、联系人辅助搜索、个人日历、会议纪要/妙记和文档。个人单聊自动发现至少需要 `im:chat:read`、`im:message:readonly`、`im:message.p2p_msg:get_as_user`；按姓名辅助查找人员再申请 `contact:user:search`。群聊还需要 `im:message.group_msg:get_as_user`。`search:message` 不属于当前主链。
4. 只有需要机器人补充入口时，才把机器人加入专门测试群并在“机器人补充入口”填写群 ID。主人个人信息流的人员/群聊选择不使用这个群 ID，也不要求机器人入群。
5. 在设置的飞书主卡中填写 App ID、App Secret、回调地址和 OAuth scope，并勾选“允许真实飞书连接”。展开“权限申请操作指南”后，先复制“开放平台批量权限 JSON”到飞书开放平台申请权限，等待批准并发布应用版本；再点击“填入推荐 OAuth scope”，把主人授权时要请求的 user scope 写入程序。两段文本用途不同，不能互相粘贴。
6. 点击“检查连接”，或直接点击“保存并开始授权”。授权按钮会先自动保存当前飞书配置，再打开浏览器；只使用最新打开的授权页，旧页面会被程序判定失效。回调页会显示授权码换 Token 的官方错误码；如果页面提示“令牌已保存，但主人身份读取失败”，说明授权本身成功，只需按提示补权限或重新授权。

Scope 和刷新令牌的本地语义是固定的：provider 省略 scope 时沿用上次已验证范围；明确返回空 scope 会清空本地授权门禁；非空 scope 会替换旧范围；null、非法类型或非法 token 会明确拒绝，不会当作 omitted/default。并发刷新会先用同一锁内完整 snapshot，再取得按身份的跨进程 durable refresh lease；租约原子绑定 generation、refresh token 指纹、owner、owner PID 与 fencing token，同一身份只允许一次 provider 交换，其他实例等待并复用赢家结果或安全失败，不会丢弃旋转 token；只有 owner 进程已退出时过期租约才可接管。provider 已开始但结果不确定时会固定为 `recovery_required`，相同或无法证明变化的旧凭据不能重试；主人完成重新授权并持久化了新 generation 与不同 refresh fingerprint 后，才会覆盖旧 marker 并取得新 lease。配置代际 CAS 或租约丢失不会伪报成功。桌面写入中断、journal/LKG、generation、settings 或 secrets 损坏时会拒绝读取/更新，不会用默认配置与旧密钥混读；迟到 owner 身份响应不会覆盖主人资料或同步状态。以上只由虚拟 token、Mock 和本地配置夹具验证，不代表真实租户 scope 缩权或 L5/L6 OAuth 轮换验收。

候选卡中的飞书文档只有在你点击后才会请求系统浏览器打开。文档地址必须是 `feishu.cn` / `larksuite.com` 下精确的 HTTPS Docx、Wiki 或 Sheets 两段路径；带 query、fragment、尾斜线或额外路径的地址会被拒绝。OAuth 只使用程序自己生成的官方授权地址，不能从候选文档入口打开。拒绝时页面会显示固定原因和 `EXTERNAL_URL_...` 错误码，不会展示完整敏感 URL；排障时只记录该错误码，不要把 URL 中的 token、query 或 fragment 复制到日志或 Issue。
7. 授权成功后，在“我的个人信息流 → 选择要关注的个人和群聊”点击“刷新列表”。系统只发现可选的既有个人单聊，默认一个也不关注。你可以逐个勾选，或点击“关注所有人”立即启用当前已发现的全部人员；以后新发现的人仍保持关闭。姓名搜索只用于确认同名人员，不会因为搜索本身开始读取。群聊可按群名筛选，页面不会要求你填写 `chat_id`。
8. 逐个选择人员或群聊后点击“保存范围设置”；“关注所有人”本身会立即保存当前人员范围。取消关注后，刷新、重启或改名都不会自动复开；重新勾选只从当前时间继续，不补收未关注期间消息。群聊仍由你明确选择，并只把真实 `@你` 消息送入候选判断。
9. 个人信息流会在桌面程序启动后自动运行。普通私聊、群聊 `@我`、日历和妙记都可分别“重新同步”；“同步全部”用于人工触发当前已配置主链。结果会明确显示 `success（成功）`、`partial_success（部分成功）`、`skipped（已跳过）` 或 `failure（失败）`；failure 不表示“当前配置跳过”，应先查看对应来源状态再重试。
同步结果下方会列出每个来源的固定状态、脱敏错误码、处理计数、耗时、陈旧提示和实际提供的下次重试时间；后端未提供的队列、退避、磁盘或新鲜度指标不会被页面猜测。设置页和“日志与纠错”页还会分开展示进程 `liveness` 与系统 `readiness`：`系统就绪`、`部分受限`、`暂不可用` 均带固定原因说明。同步或健康刷新只接受最新请求，重复点击会保持忙碌状态；这些 UI 证据仅来自 synthetic browser Mock，不代表真实飞书、LLM 或 Windows L5/L6。
10. 让任一当前已被飞书会话列表发现、且未被排除的联系人发一条私聊，或在已选择群里真实 `@你` 发出测试需求；确认“日志与纠错 → 连接健康”有成功记录，候选收件箱出现一条候选。对方消息只会形成待主人确认的候选；当主人随后明确说“我来做”或“我负责”时，Issue #19 的主人状态机可在安全门通过后自动承接并建立私人任务，但不会自动回复对方。

“填入推荐 OAuth scope”当前写入以下 user scope；只保留你已经在开放平台批准并发布的项目：

```text
offline_access contact:user:search im:chat:read im:message:readonly im:message.p2p_msg:get_as_user im:message.group_msg:get_as_user calendar:calendar:readonly minutes:minutes.search:read minutes:minutes.basic:read minutes:minutes.artifacts:read minutes:minutes.transcript:export docx:document:readonly wiki:node:read
```

折叠指南中的“开放平台批量权限 JSON”是另一种格式：`user` 数组服务于主人个人信息流，`tenant` 数组只服务于可选的机器人补充入口。它用于开放平台的批量导入，不应粘贴到 OAuth scope 输入框。

## 4. LLM 配置

默认 `rule_mock` 不联网。真实模式使用 OpenAI-compatible API：

- `Provider`：例如 `openai_compatible`；
- `API Base`：填写服务商的根地址，通常到 `/v1`；
- `Model`：填写服务商支持的精确模型名；
- `API Key`：只保存到 Windows 安全凭证存储；
- 超时和最大重试次数：按服务商限流情况调整。

### DeepSeek 示例

```text
Provider: deepseek
Model: deepseek-v4-flash
API Base: https://api.deepseek.com
API Key: DeepSeek 控制台生成的 Key
超时: 60000
最大重试次数: 2
```

需要更强能力时，模型可改为 `deepseek-v4-pro`。以上模型名按 2026-08-10 的 DeepSeek 官方文档记录；若控制台后续显示不同模型，应以控制台当前可用的精确名称为准。程序会在 API Base 后自动追加 `/chat/completions`，所以 API Base 不要填写完整接口路径。

当前 DeepSeek 兼容层会关闭 thinking，并要求最终正文返回 JSON。出现 HTTP 200 但只有 `reasoning_content`、正文为空或 `finish_reason=length` 时，程序会重试，不会把推理过程或半截 JSON 当成成功；连接检查只有实际得到 `{"ok":true}` 才会显示 `ready`。

### 公司统一网关

- `Provider`：填 `company_gateway` 等便于日志识别的名称；若网关后端是 DeepSeek，建议名称包含 `deepseek`，让程序使用 DeepSeek 兼容的 JSON 输出模式。
- `Model`：填写公司平台给出的精确模型别名，不能自行猜测。
- `API Base`：填写 OpenAI-compatible 根地址，通常到 `/v1`，不要包含 `/chat/completions`。
- `API Key`：填写公司网关颁发的 Token。
- 当前程序固定使用 `Authorization: Bearer <Token>` 和 `POST <API Base>/chat/completions`。如果公司网关要求额外 Header、签名或非 Bearer 鉴权，当前版本还不能直接使用，需要先扩展适配器。

系统把消息裁剪和脱敏后发送给模型，并保存 provider、model、prompt 版本、输入哈希、耗时、重试和结构化结果元数据。模型失败、超时、限流或返回无效 JSON 时，系统先重试；最终仍失败时只保留来源和恢复工作项，不生成候选任务卡。规则判断可用于安全分流，但“规则降级成功”不等于模型调用成功。

模型最终失败时，打开“候选收件箱”顶部的“失败来源收件箱”。这里不会显示聊天正文，只显示来源类型、时间、失败阶段、固定错误码、尝试次数和是否陈旧。服务端会同时核对失败记录、拥有它的来源、原始 Runtime job 的 revision/source set 和 `job_source_link`；关系损坏的记录不会进入列表，直接操作只返回固定脱敏错误且不改变任何业务或审计数据。点击“重试”会继续处理本机已经保存的来源，不扩大飞书读取范围、不重新生成来源、不发送任何外部消息；重复点击只会返回同一个排队状态。成功后失败记录会标记“已恢复”，候选会回到普通列表；无法再处理的记录可以“归档”，来源和私有审计仍保留。

为避免一条消息带入过多文档，当前最多把 8 篇文档交给判断链：单篇正文最多 8,000 字，文档正文合计最多 12,000 字，最终结构化模型输入最多 20,000 字。超出部分不会直接拼进 Prompt；受限、过期缓存和未读取类型都会作为状态告知模型，不能伪装成完整事实。

连接测试分别检查飞书和模型，不要把其中一个成功理解成另一个也已连接。模型供应商可能看到被发送的脱敏内容并产生费用，真实使用前应确认公司和个人数据政策。

## 5. 常见问题

涉及 Windows 安装包、Electron 或旧 OAuth 设置页的条目仅作遗留排障记录；现行用户从 Cindy 插件和浏览器入口开始。

| 现象 | 先做什么 |
| --- | --- |
| SmartScreen 阻止安装 | 核对下载来源和校验值；当前版本未承诺商业代码签名。 |
| OAuth 回调失败 | 先看回调页的官方 `code`、HTTP 状态和说明：`token_exchange` 表示授权码换 Token 失败；`owner_identity` 表示 Token 已保存但用户身份读取失败。授权码只能使用一次，重试时要重新点击“保存并开始授权”。 |
| OAuth 官方 code `20049` | 这是 PKCE 校验失败，不是 scope 错误。旧安装包曾发送不兼容的 PKCE 参数；升级到 2026-08-11 之后的修复包，关闭全部旧授权页，再从程序重新点击授权。 |
| OAuth 权限范围为空 | 这不是回调地址错误，但授权只会包含 `offline_access`；先在开放平台申请并批准实际所需 scope，再点击“填入推荐 OAuth scope”或手工粘贴。授权按钮会自动保存。 |
| 来源显示“需要管理员批准”或“权限受限” | 当前 Token 没有该来源所需的 user scope。程序会安全跳过本轮，不请求消息 API、不推进游标；在开放平台批准并发布权限后重新授权，再点击对应来源的“重新同步”。 |
| 刷新后找不到某位联系人 | 先输入姓名搜索并根据部门/邮箱确认；还要检查 `contact:user:search` 是否已批准、发布并重新授权。没有既有 P2P 时会显示“未找到现有单聊”，程序不会创建会话。 |
| 某人的私聊没有进入候选 | 点击“刷新列表”，确认该人员已被飞书返回且没有被你排除，并批准 `im:chat:read`、`im:message:readonly`、`im:message.p2p_msg:get_as_user`。普通私聊是周期轮询，不是实时事件；主人自己发出的消息不会建候选。 |
| 群聊 `@我` 没有进入候选 | 确认该群已在“关注群聊”中选择并保存、系统主人确实在群内、消息真实 `@你`，并批准 `im:chat:read`、`im:message:readonly`、`im:message.group_msg:get_as_user`。主人用户身份主链不要求机器人入群。 |
| DeepSeek 提示“模型没有返回可解析的内容” | 旧版连接检查只允许 16 个输出 token，DeepSeek V4 可能先生成推理而没有留下最终正文；这不等于 Key 填错。升级到 2026-08-11 之后的修复包，再点“检查模型”。新版会关闭 thinking、提高输出预算，并校验实际返回 `{"ok":true}`。 |
| DeepSeek 连续显示“全部降级”或收不到候选 | 升级到包含 `demand_intake_v7` 的 PR #24 测试包。新版把大 JSON 拆成多个小判断，并对非法 JSON、字段类型漂移分别修复；次要阶段失败不会再让已成功的新需求消失。来源仍会先保存，核心动作或摘要连续失败时由 Runtime 有限重试。 |
| 设置页同时出现“CONFIGURED”和“暂未配置 / 不会保存” | 这是旧版把浏览器开发用的临时格式校验表也显示在 EXE 中；它不会读取桌面配置，所以看起来相互矛盾，但不代表配置丢失。升级后 EXE 只显示真实设置，临时表只保留在浏览器开发模式。 |
| Windows 提示无法打开 `disabled` 链接 | 旧安装包在未启用真实飞书时会生成伪协议；请先开启真实连接、填写 App ID/Secret 并保存，或升级到修复后的安装包。 |
| 点击飞书文档后提示“链接被拒绝” | 确认地址是 `https://`，域名确实以 `.feishu.cn` 或 `.larksuite.com` 结束，且路径严格为 `/docx/<token>`、`/wiki/<token>` 或 `/sheets/<token>`。当前不接受 query、fragment、尾斜线、额外路径、用户名密码或跳转参数。不要粘贴完整敏感 URL 到日志；真实租户域仍需在明确授权的 L6 步骤中验收。 |
| 401/403 | 重新授权；检查 App ID/Secret、scope 和管理员批准。 |
| 文档显示“无权限 / 暂不支持” | 原消息仍已保存。确认 `docx:document:readonly`、`wiki:node:read` 已申请、批准、发布并重新授权；Sheet、Base、旧版 Doc、File、Slides 当前只识别链接。 |
| 文档显示“缓存内容可能已过期” | 临时网络或服务错误发生时，系统保留上次成功读取的版本。它只能作为待确认背景；点击来源重新同步，或等待下一轮到期刷新。 |
| 后续补充被识别成新任务 | 确认消息是否使用回复链，或是否明确写出“补充 / 追加 / 继续”。如果同一会话存在多个近期任务，系统会要求主人确认关联，不会自动猜测。 |
| 后续消息为什么没有自动更新 | 检查全局是否为“仅建议”、该任务是否暂停、关联是否唯一、模型是否降级、置信度是否达标，以及时间是否标为待确认。来源已经保存，可在待确认提案中人工处理。 |
| AI 自动改错了 | 打开任务详情 → AI 最近修改。若它仍是最新任务版本，点击“撤销这次修改”；若已有后续修改，使用“编辑任务”纠正最新字段，系统会保留完整审计。 |
| AI 把任务标为完成或归档 | 只有明确完成、取消或不再处理证据才允许自动写入，并会重点提示。证据不正确时立即撤销或编辑；AI 不能自动删除任务或判定“这不是需求”。 |
| 模型失败后为什么没有马上再次调用 | 周期同步遵守 Runtime 的指数退避，避免反复请求；来源已保存，不会丢失。显式人工重试才会提前唤醒失败判断。 |
| 模型结构失败后候选去哪了 | 来源仍在 SQLite，系统不会把它当成“不是需求”。Runtime 会有限重试并按退避恢复；在模型成功整理前不会生成候选任务卡，旧版“AI 整理待重试 / 0%”占位也会自动隐藏。聊天正文不会被塞进摘要。 |
| 失败来源收件箱显示什么 | 只显示来源类型、发生时间、AI 分类阶段、固定错误码、Runtime 状态、尝试次数和陈旧提示；不会显示聊天正文或外部消息 ID。服务端还会校验来源、原始 job payload 和 `job_source_link` 关系，失效记录会被安全隐藏。主人可以重试或归档，成功、再次失败和归档都会保留私有审计。 |
| 点击失败来源重试多次会不会重复建单 | 不会。重试沿用同一来源、同一分类 revision 和 Runtime job；服务端用状态/CAS 防止重复点击创建第二个工作项。成功后只生成一份候选或后续需求线程。 |
| 失败来源显示“已陈旧” | 说明来源或受控文档背景已经变化，旧失败结果不能覆盖新版本。请等待新的分类轮次，或重新同步来源；旧记录可以归档，原始来源仍保留。 |
| 一段聊天里有两件需求 | 系统会按需求单元拆成两张卡，并分别关联已有需求线或任务；共享来源摘要仍可在两张卡中查看，聊天正文只保留在本地审计。若拆错，可按具体需求纠正，不会连带移动另一件事。 |
| 卡片提示“背景不完整” | 有界补扫达到 72 小时、3 页、硬起点或权限边界。现有来源没有丢失，但 AI 不能保证看到了更早背景；请查看原始来源后确认，必要时人工补充。 |
| 接受任务后为什么没看到文件夹 | EXE 会自动使用自己的应用数据目录。打开任务详情 → 持续更新 → 任务记忆目录；如果显示失败，先点“重试任务记忆”，成功后点“打开任务记忆目录”。实际工作目录引用仍然只读。 |
| 清理任务记忆会不会删附件 | 不会。它只删除系统托管清单中的标准投影文件；未知文件、用户附件和真实工作目录都保留。 |
| 解除参考路径会不会删除工作文件 | 不会。解除只删除本地绑定和引用快照，不向真实目录执行删除、移动或修改。 |
| 机器人收不到群消息 | 确认机器人已入群、群 ID 填写正确、真实连接开关已打开。 |
| 立即扫描显示跳过 | 普通私聊尚未发现可读 P2P、所有人员都被排除，或群聊没有选择对象时会安全跳过；先刷新范围，再检查主人 OAuth 和对应权限。日历、妙记仍按各自权限诊断。 |
| 429/超时 | 减少扫描频率、检查模型重试设置，等待限流窗口结束。 |
| 日历/妙记详情连续网络失败 | 程序会按受控次数重试真实 transport Error；耗尽后显示 `failure`，保留旧 cursor/watermark/checkpoint 和已有完整来源。修复网络后重新同步即可；不要手工修改水位，也不要把权限不足的 partial 与网络失败混淆。 |
| 窗口“关闭”后找不到 | 查看系统托盘；选择“完全退出”才会退出。 |
| reference 检查失败 | 重新用原生目录选择器授权；目录移动或撤销后不会自动恢复权限。 |
| 误接受了一条需求 | 打开任务详情 → 纠错 → 选择“这不是需求”；系统只修改本机任务台账，不会通知需求方。 |
| 任务从列表中消失 | 先打开“归档与回收站”；它可能已归档或被移入回收站。回收站任务可恢复。 |
| 候选从收件箱消失 | 先检查候选页的“回收站”筛选。未接受候选可单独恢复；已接受候选恢复时会同时恢复正式任务。来源和审计不会被删除。 |
| 同一聊天的两条候选没有合并 | 同一会话或时间接近只是线索，不足以证明同一需求。若业务对象、目标或交付不同，系统会保留两件事；若只是低置信，会在其中一张卡显示归并建议。 |
| AI 选错了“我需要推进”的主体 | 在接受正式任务前展开原始来源，对正确的一条点击“设为主体”。该操作只改本机任务库记录并留下审计。 |
| 两件事被错误合并 | 在接受前展开原始来源，对应消息点击“拆成独立候选”。接受后需使用正式任务纠错，候选页不会直接拆开已建立的任务。 |
| 计划时间保存失败 | 检查计划完成是否早于计划开始；若提示版本冲突，关闭详情后重新打开，再保存最新值。 |

## 6. 日志、纠错和诊断包

“日志与纠错”页面可按类型、级别、开始日期和结束日期查看：运行日志、连接健康、模型判断、失败/重试、任务时间线、Outbox 和 `correction_event`。设置页可配置 1—365 天的运行日志保留期；程序每次启动或重新加载配置时自动清理到期记录，也可以一键删除当前运行诊断日志。任务、原始来源和纠错审计不会被普通日志删除按钮移除。

人工触发同步后，设置页会明确显示：`success`（成功）、`partial_success`（部分成功）、`skipped`（已跳过）和 `failure`（失败）；partial/skipped/failure 都不会显示成“同步完成”。来源级计数、错误码、耗时、stale 和 next retry 仍以安全同步结果/诊断为准。排障时可记录 `operation_id`、`request_id`、`trace_id` 和 `span_id`，但不要把它们理解为真实飞书请求 ID。连接状态中的 `ready` 表示本地依赖全部满足，`degraded` 表示某个依赖需要查看且必须带受控 reason，`not_ready` 表示本地数据库等硬依赖不可用；设置页会把 liveness、依赖 readiness 和最近连接检查分开显示，诊断 JSON 仍保留完整受控字段。

“导出脱敏诊断包”是用户主动选择保存位置的 JSON。它包含桌面版本、平台、是否为安装包运行、release identity、readiness、后端操作/请求/trace ID、组件状态、计数、错误码、耗时、有限 recent events、队列/退避/同步摘要和固定 limits；不包含密钥、完整聊天原文、完整 prompt/response 或本地绝对路径。导出后可把文件交给协作者排查。清理日志不会删除任务或原始来源。

日志、连接健康和诊断包当前记录 `redactionSchemaVersion: 1`。程序会在写入前递归清理嵌套对象、数组和错误原因，并在页面读取或导出时再清理一次；Authorization/Bearer、多值 Cookie、URL query、`file://`、本机绝对路径、凭证字段和可能的正文默认显示为占位符。无法识别的字段不会回显原值；事件数量、详情长度和诊断包 recent 列表也有固定上限。详细字典见 [日志与诊断数据字典](diagnostics.md)。
